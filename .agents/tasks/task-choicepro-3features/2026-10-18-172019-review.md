# Profile editing, faculty/dept seed, carryover CGPA support

Three features were added across 17 files: students can edit their profiles after registration, the database ships with all 11 faculties and their departments, and carryover course results are tracked separately so CGPA deduplicates by taking the best attempt per course. The admin course pages were also opened up to any admin (not just super-admin), and courses gained an `isCarryOver` flag used both at creation time and at result entry.

**Watch for:** The profile edit UI (`app/dashboard/profile/edit/page.tsx`) and its companion API route (`app/api/user/profile/route.ts`) are **untracked files — not committed**. The only committed part of the profile-edit feature is the PATCH handler on `app/api/student/profile/route.ts`, which is also not staged. The primary user-facing deliverable for "users should be able to edit their profiles after registration" will not reach any deployed environment until these files are committed. — **confirmed**

The unique index on Result (`studentId + courseId + sessionId + semester`) was dropped entirely rather than made conditional. This removes the last database-level guard against duplicate normal results. — **confirmed**

## High-level view

The profile-edit flow is split across two new files (`/dashboard/profile/edit/page.tsx` and `/api/user/profile/route.ts`) plus the patched PATCH handler on `/api/student/profile/route.ts`. All three are untracked and unstaged, so the feature exists on disk but is not in version control and will not be deployed. The PATCH handler itself is solid — Zod validation, matric-number uniqueness check against other students, `$set` with `runValidators`, 404 when no profile exists.

The seed script covers all 11 faculties and 63 departments exactly as specified, uses `findOneAndUpdate` with `upsert: true` against both `code` and `name`, and is fully idempotent. The `facultyIdMap` pattern correctly resolves department→faculty foreign keys without a second round-trip.

The CGPA deduplication in `lib/cgpa.ts` is straightforward: build a Map keyed by `courseId`, keep the highest `gradePoint` entry, then compute the weighted average. The analytics page now passes `courseId` through to `calculateCGPA` and uses `calculateGPA` (no deduplication) for per-semester GPA — the right separation. However, `calculateGPA` is still exported from `lib/utils.ts` and is also used by the analytics page's per-semester path; these two functions now have divergent semantics that callers need to keep straight.

Dropping the unique compound index on `Result` removes the only database-level guard against true duplicates. The carryover bypass (`if (!validatedData.isCarryOver) { ... }`) in the API is a client-controlled gate: any client that sends `isCarryOver: true` can insert an unlimited number of results for the same course in the same semester without any server-side frequency cap. The old index would have caught accidental double-submissions from normal flows; without it, a network retry on a non-carryover POST can create silent duplicates.

The admin auth change (`isSuperAdmin` → `isAdmin`) is backed by the `check-super-admin` API already returning an `isAdmin` field, so the runtime check is sound. The API-level guards on courses POST and PUT both check `session.user.role !== "ADMIN"` directly, consistent with the rest of the admin surface.

`Student.carryOverCourses` is defined in the model and interface but nothing in this diff writes to or reads from it. It appears to be scaffolding for a future workflow (e.g., pre-registering carryover courses) that was never wired up.

3. **`isCarryOver` is fully client-controlled** — The duplicate-check bypass is gated only on `validatedData.isCarryOver`, which comes from the request body. A student can mark any result as a carryover to skip the duplicate check. Consider verifying against the student's actual `carryOverCourses` list or at minimum against whether a failing result for that courseId already exists before allowing a carryover insert.

4. **`Student.carryOverCourses` is dead field** — The field is modelled but never populated or queried in any changed file. Either wire it up to the carryover result-entry flow (populate it when a carryover result is created, query it in the duplicate-check logic), or remove it to avoid schema drift.

The feature is functionally complete on disk but invisible to git.

### Unique index removal and carryover bypass

```
- ResultSchema.index({ studentId: 1, courseId: 1, sessionId: 1, semester: 1 }, { unique: true })
+ ResultSchema.index({ studentId: 1, courseId: 1 })
```

The replacement index is non-unique, making it purely a query hint. The application-level duplicate check is still present for non-carryover results, but it queries by `studentId + courseId + sessionId + semester` — so a retry with the same payload (but `isCarryOver: false`) can still slip through between the check and the insert under concurrent requests. For carryover results there is no check at all: the same `courseId` can be inserted as many times as the client wants in the same session/semester. The previous unique index was the backstop for both cases.

### `Student.carryOverCourses` scaffolding

The interface and schema both declare `carryOverCourses` as an optional array of `{ courseId, level, semester, originalSession }`. No route in this diff writes to it when a carryover result is created, and no route reads it to validate whether a result being flagged as carryover is actually registered as such for this student. It's dead weight until the write path is wired up.
